# Hook fixtures

Recorded provider hook payloads. They are the input of the conformance tests
that every provider crate runs (see `limpid_agent_model::conformance`), and
the reference for what each agent actually sends, as opposed to what its
documentation says.

## Layout

```
fixtures/
  <provider>/<schema-date>/<case>/
    NNNN-<HookEventName>.json                one raw payload per hook call, in order
    NNNN-<HookEventName>.transcript.jsonl    Claude only: the transcript at that moment
    expected.json                            neutral events per payload (array of arrays)
    approval.expected.json                   only for approval cases: the ApprovalRequest
  negative/
    <case>.json                              inputs every adapter must reject or pass through
```

`<schema-date>` is the year and month the payloads were recorded, for example
`2026-09`. When a provider changes its hook schema, record a new dated
directory and keep the old one: both must keep passing, because users update
the agent and Limpid at different times.

`expected.json` holds one array per payload file, in file order. An empty
inner array means the payload produces no event. `approval.expected.json`
maps payload file names to the `ApprovalRequest` the adapter derives from
them (`null` for a payload that must not be treated as an approval); every
payload the file does not list must yield no request.

`negative/` holds inputs every adapter must handle the same way: an error
for input that is too large or not a JSON object, and exactly one
`Extension` event for an unknown event name. The oversized case is
synthesized by the driver rather than stored. Control characters inside a
title are not a negative input for `normalize`, which passes strings through
unchanged; the record rules sanitize them, and that is tested there.

`expected.json` is regenerated by `scripts/derive-expected-events.py`, which
mirrors the adapters' fallback order so a re-recorded case does not have to be
written out by hand. The committed files are the goldens: re-run the script
after re-recording a case and review the diff. When the script and an adapter
disagree, review decides which behavior is correct and the script is updated
to match.

## Running the conformance tests

Each provider crate has a `tests/conformance.rs` of this shape, with the
model crate's `conformance` feature enabled as a dev-dependency:

```rust
use limpid_agent_model::conformance::{run_approval, run_negative, run_normalize};
use std::path::Path;

fn fixtures(segment: &str) -> std::path::PathBuf {
    Path::new(env!("CARGO_MANIFEST_DIR")).join("../fixtures").join(segment)
}

#[test]
fn payloads_normalize_as_recorded() {
    let failures = run_normalize(&limpid_provider_claude::ClaudeAdapter, &fixtures("claude"));
    assert!(failures.is_empty(), "{}", failures.iter().map(ToString::to_string).collect::<Vec<_>>().join("\n"));
}
```

`run_approval` and `run_negative` follow the same pattern.

## Recording

`scripts/record-hook-fixtures.sh` launches one agent session under the Debug
build's shim with `LIMPID_HOOK_RECORD_DIR` set, inside a detached tmux session
that is then driven with `tmux send-keys`. Both backend receivers save every
payload they receive, byte for byte, before doing anything else with it.

```
scripts/record-hook-fixtures.sh claude session-basic /tmp/recordings
tmux send-keys -t rec-claude-session-basic 'list the files here' Enter
tmux send-keys -t rec-claude-session-basic '/exit' Enter
```

Notes that shaped the recorded cases:

- Claude's `PermissionRequest` normally goes to the approval helper, not to
  `limpid-hook`. To capture it, the case passes a user `--settings` value that
  adds a second `PermissionRequest` hook pointing at the recorder; the shim
  merges user settings with its own.
- Codex only runs hooks whose trust hash is in `~/.codex/config.toml`, which
  only the app writes. Launch the Debug app once before recording so the block
  matches the Debug bundle; `scripts/codex-hook-args.py` checks this and
  builds the same `-c` flags the app hands a pane.
- Codex's `PermissionRequest` reaches the recorder through the approval
  helper's lifecycle fallback, which runs only when the helper cannot reach
  the approval service. Record it with the Debug service unregistered
  (`LIMPID_AGENT_SERVICE_CONTROL=unregister` on a Debug launch) so the native
  Codex prompt appears and the payload is captured.
- The recording sessions run outside tmux from the agent's point of view;
  `TMUX` and `TMUX_PANE` are removed so the payloads have the ordinary
  non-hosted shape. `claude/tmux-hosted` keeps them.

Cases that could not be recorded as planned:

- `codex/stop-error` does not exist. Codex's `stop.command.input` schema
  (2026-09) has no error field and forbids additional properties, so a turn
  that fails never reaches `Stop` with an error; the transport retries or the
  session reports the failure without a hook. The `Failed` event therefore has
  no Codex source today.
- `claude/stop-failure` carries the error under `error`, not `error_type` as
  the shell receiver expected; the fixture keeps the real key.
- `claude/title` was recorded over three turns, but Claude Code had not written
  an `ai-title` line by the time the session ended. The last two lines of its
  final `Stop` transcript were added by hand with the shape observed in real
  transcripts (`{"type":"ai-title","aiTitle":...,"sessionId":...}` and the
  `custom-title` equivalent). While the shell receiver remains the rollback
  backend, title extraction uses only the latest `ai-title` record; the
  separate `custom-title` line remains here to guard that compatibility rule.

## Scrubbing

`scripts/scrub-hook-fixture.py <file> <case>` rewrites one recorded file in
place before it is committed:

- the home directory becomes `/Users/example`, temporary directories become
  `/tmp/example`, the encoded temporary path in Claude's transcript
  directory name becomes `-tmp-example`, and the bare account name (as `ls -l`
  prints it) becomes `example`;
- `session_id` and the other session identifiers become a fixed UUID, the
  per-turn identifiers (`prompt_id`, `turn_id`, `tool_use_id`) become one
  fixed placeholder each, and UUIDs inside path values become a fixed UUID;
- conversation text (`prompt`, `last_assistant_message`, transcript
  `content`, `display`, `text`) becomes `<key for case>`; provider-authored
  strings such as a Notification `message`, `tool_input`, and `tool_response`
  stay, because the adapters read them and their paths are already scrubbed;
- transcript copies keep only the title lines (`ai-title`, `custom-title`)
  in full; every other line is reduced to its `type`.

Key names, event names, field types, and file order are never changed.
Fixtures are reviewed like code: read every recorded file before committing
it, because the rules above cover what the recorder has produced so far, not
every field a future provider version may add.

## Naming

Case names use lowercase words joined by `-`. Payload files keep the
zero-padded sequence number the recorder assigned so the order of hook calls
is preserved even when a case is re-recorded.
