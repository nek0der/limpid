# ADR 0004: Provider Adapter Contract

- Status: Accepted.
- Date: 2026-09-14.
- Amends: ADR 0002 by defining the provider adapter, the neutral event
  vocabulary, and the split of the portable rules into `apply`, `project`,
  `on_launch`, and `on_terminate`; and by recording that a second operating
  system is not planned, so the portability that ADR 0002 motivates is kept as a
  dependency constraint on the Rust crates rather than as a roadmap item.

## Context

Before this migration, Limpid observed Claude Code and Codex through provider
hooks whose receivers were two shell scripts (`limpid-hook` per provider). They
mapped hook events to a per-run state record, wrote resume hints and cwd events,
captured turn snapshots, and intercepted `git worktree add`. The application
side consists of four Swift trackers plus attention, notification, and cleanup
rules. The Swift twin files under `Core/Claude` and `Core/Codex` are already
generic over `AgentSpec`; the real duplication is the event-to-state rule set
that exists once per shell script, and the provider-specific approval
translation in `AgentApprovalHookAdapter.swift`.

This change implements the crate layout, provider adapters, approval
translation, `apply`, and the hook runtime. The application-side `project`,
`on_launch`, and `on_terminate` rules followed in a second change, which
replaced the per-provider Swift trackers with one projection adapter that
reads the directories, asks the rules, and applies the answer.

ADR 0002 assigns provider input normalization, output models, and
provider-neutral event and projection rules to the portable Rust core, but it
does not say how a provider is added, which behavior differences are provider
capabilities, or which rules run in the hook process versus the application.
Adding a third agent today means editing both shells, the Swift registry, and
`Tab`, and a change in a provider's hook schema has no recorded contract to
test against.

A second operating system is not planned. Portability is therefore a
constraint on crate dependencies, not a phase.

## Decision

### Crate layout and dependency rules

```
rust/
  limpid-agent-model/      vocabulary: ProviderId, Capability, ProviderDescriptor,
                           AgentEvent, RunRecord, approval types, adapter trait
  limpid-agent-core/       rules: apply, project, on_launch, on_terminate,
                           ApprovalBroker (existing)
  limpid-agent-protocol/   wire, framing, session (existing)
  limpid-agent-hook/       hook runtime: normalize, apply, locked atomic writes,
                           tmux endpoint, turn snapshot, worktree intercept
  limpid-provider-claude/  Claude Code adapter
  limpid-provider-codex/   Codex CLI adapter
  limpid-rust-bridge/      C ABI facade (existing); header generated by cbindgen
  fixtures/                recorded provider payloads for conformance tests
```

`limpid-agent-model` and `limpid-agent-core` do not depend on any provider
crate and hold no registry; `ProviderId` validates only its string form
(lowercase ASCII letters, digits, and `-`, 1 to 32 bytes). A provider crate
depends only on the model crate. Only the hook runtime depends on every
provider and holds the registry; the bridge resolves an id through it. No
crate links a transport or a terminal engine. New dependencies are limited to
MIT, Apache-2.0, and MPL-2.0 licenses.

The executables stay Swift. The Hook Helper and the Agent Integration Service
link the bridge as a static library and call it through the versioned C ABI
with JSON envelopes. The helper performs the approval XPC round trip; Rust holds
translation and rules only.

### Provider adapter

A provider is one crate that implements one trait and publishes a descriptor.

```rust
pub trait ProviderAdapter: Send + Sync {
    fn descriptor(&self) -> &ProviderDescriptor;
    fn install_recipe(&self) -> InstallRecipe;
    fn normalize(&self, input: RawHookInput<'_>, ctx: &HookContext)
        -> Result<Vec<AgentEvent>, NormalizeError>;
    fn approval_request(&self, input: RawHookInput<'_>)
        -> Result<Option<ApprovalRequest>, NormalizeError>;
    fn approval_output(&self, decision: &ApprovalDecision, request: &Value) -> ProviderOutput;

    // Optional; each has a default implementation returning nothing.
    fn transcript_path(&self, input: RawHookInput<'_>)
        -> Result<Option<String>, NormalizeError>;
    fn title_index_path(&self, input: RawHookInput<'_>, ctx: &HookContext)
        -> Result<Option<PathBuf>, NormalizeError>;
    fn indexed_titles(&self, input: RawHookInput<'_>, index: &[u8]) -> Option<Titles>;
    fn worktree_intent(&self, input: RawHookInput<'_>)
        -> Result<Option<WorktreeIntent>, NormalizeError>;
}
```

- `ProviderDescriptor` carries the stable id, display name, capability set,
  PID sweep interval, state, session, and cwd-event directory names, and the
  process names used for the parent-process walk. Directory names default to
  `<provider_id>-agent-states`, `<provider_id>-sessions`, and
  `<provider_id>-cwd-events`; Claude alone declares the legacy names
  `agent-states`, `sessions`, and `cwd-events` so no data moves.
- `normalize` turns one raw hook payload into neutral events. Unknown event
  names become `AgentEvent::Extension { name, payload }` with the original
  payload, so a provider's new event is visible before the core understands
  it. Unrecognized fields on known events are ignored.
- `approval_request` and `approval_output` replace the Swift approval
  translation. The decision vocabulary is `allow_once`, `deny`, `delegate`,
  and `answer`. A decision joins the protocol, the `hello` capabilities, and
  the broker together; `ask` joins them the same way only when a provider that
  emits it is integrated. An `answer` decision is rendered by the provider that
  asked the question; every other provider delegates it. `approval_output`
  receives the whole `ApprovalRequest` document, so the adapter renders an
  answer only when its `tool_name` is the provider's question tool.
- `install_recipe` declares the settings fragments, environment variables, and
  PATH shims the platform must place. The adapter never touches the file
  system.
- A recipe names what the platform substitutes with a `RecipePlaceholder`
  rather than a literal token. The tokens were strings on both sides, where a
  typo compiles, installs, and then leaves the agent reporting to nothing.
- `transcript_path` names the transcript the runtime should read alongside a
  payload, so a provider that keeps one pays the extra file read only on the
  events whose normalization uses it.
- `title_index_path` names the file where a provider keeps its session titles
  apart from the transcript (Codex's `session_index.jsonl` under its home).
  The runtime reads that file's tail, `indexed_titles` reads the titles of
  the payload's session out of it, and the runtime adds them to the events
  that carry titles (`AgentEvent::add_titles`). Claude keeps its titles in
  its transcript, which `normalize` already reads.
- `worktree_intent` reports a `git worktree add` the agent is about to run, so
  the runtime can intercept it before the tool runs; it is separate from the
  neutral events because it is a request to act, not an observation.

Where an intercepted worktree goes is read from `worktree-routing.json`, which
the application writes beside its session file in the same operation. The hook
read the session file itself until it stopped finding any projects after they
moved into the sidebar's containers, and created worktrees in the wrong place
until someone noticed. The routing file is narrow enough to be stable, is
versioned, and is left alone by a hook that does not recognize the version:
passing the command through puts the worktree where the agent asked, which is
recoverable, whereas guessing at an unknown shape could put it anywhere.

Input limits: a hook payload is at most 1 MiB, the same bound the protocol
places on a client request, and record prompt, title, and detail fields are
cleaned and truncated to 4096 bytes, including values carried from a v2 record.
A transcript tail is at most 4 MiB and is read only from a regular file.

### Capabilities

The core and the UI branch on capabilities, never on provider ids.

| Capability | Meaning | Claude | Codex |
| --- | --- | --- | --- |
| `session_end_drops_session` | `SessionEnd` may delete the resume hint. | yes | no |
| `resume` | A resume command can be generated. | yes | yes |
| `resume_defers_to_other_live_session` | Resume yields to another provider's live session in the pane. | no | yes |
| `cwd_events` | The provider reports working-directory changes. | yes | no |
| `worktree_events` | The provider reports worktree creation. | yes | yes |
| `approval_hook` | Approval is answered by a hook process. | yes | yes |
| `approval_protocol` | Approval is requested over a connection. | no | no |
| `subagents` | The provider emits subagent events. | yes | yes |
| `turn_snapshot` | Turns are recorded: a snapshot on prompt submit and another when the turn ends. | yes | yes |
| `cache_window` | The provider reports when its prompt cache expires, on `TurnFinished`. | yes | no |

### Event vocabulary

`SessionStarted`, `SessionEnded`, `PromptSubmitted`, `ToolStarted`,
`ToolFinished`, `WaitingForInput`, `ApprovalRequested`, `Compacting`,
`CompactionFinished`, `AwaitingPrompt`, `TurnFinished`, `Failed`,
`Interrupted`, `CwdChanged`, `WorktreeCreated`, and `Extension`.

Titles are no event of their own: no provider reports a title as it
changes, so they ride on the session start, the prompt, and the turn's end,
where the adapter or the runtime observed them. A tab and a pane header are
named by the provider's title for the session, else the one it generated,
else the opening prompt, and only once the run has reported its
conversation id.

An extension is promoted to a named event only when two providers emit the same
thing. `CompactionFinished` is the recorded exception: only Codex emits it, but
it closes the existing `Compacting` event rather than introducing a concept.
`AwaitingPrompt`, Claude's idle `Notification`, is the second exception, for
the same reason (see "Work outside a turn").

### Stops that continue a turn

`TurnFinished` carries `continues_after_stop_hook`, true when the provider
reports that the stop follows work another stop hook asked for (Claude's and
Codex's `stop_hook_active`). The turn the earlier stop ended went on, so the
hook runtime takes that turn's end again. Any other stop of a turn that has
already ended is a stop with no prompt of its own, such as an agent answering
a background task; such a stop gets an end-only record rather than changing
the earlier turn. The field is omitted when false.

`TurnFinished` also carries `reply`, the agent's last reply as the provider
sent it with the stop (Claude's and Codex's `last_assistant_message`), whole.
The adapter only reads it; the core decides what a turn keeps of it
(`reply_head`), so the two providers' replies are cut by one rule.

### Work left running after a turn

`TurnFinished` also carries `background_work`, what the agent left running as
the turn ended, counted as `shells`, `subagents`, and `others`. Claude's `Stop`
lists its background tasks (`background_tasks`), and when one ends on its own
Claude begins a turn of its own from a `<task-notification>` prompt, whose
stop lists what is left. The latest stop therefore stands with no end event of
its own. A task the person stops from Claude's task list is the exception:
Claude only queues its end for the next prompt and starts no turn, so no stop
updates the count until then. `apply` stores the count on the run record
(`backgroundWork`) and clears it on `PromptSubmitted`, every
`SessionStarted`, `SessionEnded`, `Failed`, and `Interrupted`. Work outside a
turn keeps it, because the idle prompt returns the run to the rest the stop
described.

A background subagent's tools reach the hook as the run's own `PreToolUse`,
`PostToolUse`, and `PostToolUseFailure`, after the stop that launched it.
Claude names the subagent in them (`agent_id`), and the adapter carries that
as `by_subagent` on `ToolStarted` and `ToolFinished`. `apply` takes no such
tool event out of `finished` outside a turn and writes nothing for it: the
stop already counted the subagent, and its tools are not the agent at work.
The guard covers only `finished`. At `idle` and `error` no stop counted the
subagent, because a session start and a failure clear the count, so its tool
events are the one sign that work goes on; they reopen the run as any tool
does until the subagent ends. Its end starts a turn of Claude's, whose stop
settles the run; Claude holds the idle prompt back while a subagent runs
(see "Work outside a turn"). A wait that the subagent's permission prompt
opened is not a rest either, and its next tool event ends it. The agent's
own tools after a stop carry no `agent_id`, so a stop hook's continuation
still reopens the run as "Work outside a turn" below describes.

`project` passes the count to the badge only while the run rests `finished`.
Codex keeps its background terminals running after a turn too, but its
`Stop` does not list them and no hook reports their end, so its adapter
reports none rather than a count that would stay until the next stop. The
field is omitted when nothing was left running.

### Work outside a turn

One rule: an event outside a turn reopens the run and records that it is
outside a turn, and the sign that the agent settled closes it. A turn is open
while the run record has `runStartedAt`. `PromptSubmitted` sets it;
`TurnFinished`, `Failed`, `Interrupted`, `SessionEnded`, a session start other
than a compaction, and the idle prompt after a turn that stopped without a
`Stop` clear it. A compaction is not the end of a turn: one in the middle of a
turn restarts the session while the turn goes on, so a compact
`SessionStarted` keeps `runStartedAt` and leaves the run `running`, while one
the person asked for after the turn leaves the run resting in `idle`. Codex's
`CompactionFinished` likewise returns to `running` only inside a turn, and to
`idle` outside one.

Work does arrive outside a turn. Claude's TUI has sent a turn's `Stop` before
the `PreToolUse` of a tool the turn still ran, with no `Stop` after it, and a
turn that another stop hook holds open (a review gate, say) goes on for
minutes after its first `Stop`. A `ToolStarted` or `ToolFinished` then shows
the run `running` with its tool, as within a turn, but leaves `runStartedAt`
empty. From `finished`, `error`, or `idle`, the run stays in the episode it
rested in, so the event announces nothing and leaves a finish the person saw
marked as seen.

The tool event records the rest the run left in `outsideTurnRest`: `idle` for
work that began at the prompt after a session start, and `finished` otherwise
(after an error too; see below). A value other than those two reads as
`finished`. The field is kept while the stretch lasts, including through a
wait in it, and dropped once the run is in a turn or at rest.

Two events close the stretch. A `Stop` is the turn's real end, as it is for
the stop hook's turn (`stop_hook_active`): it always begins a new episode,
even from `finished`, and is announced, so a `Stop` that comes after the idle
prompt settled the stretch is announced too. Claude's idle `Notification`
(`AwaitingPrompt`) closes a stretch that no `Stop` follows: a run that is
`running` with no `runStartedAt` returns to its `outsideTurnRest` (`finished`
when a record lacks it) in the same episode, and the cache window is cleared,
because the stretch's requests refreshed the cache after the window was read.
The idle prompt closes the same stretch in the turn record: it takes the end
snapshot and difference of the run's current turn again
(`TurnStep::Retake`), so what the late tools changed is in the turn whose
`Stop` came first. The turn keeps the phase it ended in: a turn that failed or
was interrupted and then went on is still failed or interrupted, with the late
changes in it. A stretch from `idle` has no turn of its own and takes no end.

The notification rules announce a finish only after the run was seen
`running` or `compacting`, and not in the episode of the end (a finish or a
failure) that the outbox last announced or last saw with nothing to announce.
That is what keeps the stretch's finish quiet, and it is why the finish is
compared with that end rather than with the previous pass: a `Stop` and the
late tool after it can land inside one pass, which then never sees the
finish, and a finish held for a tmux pane is dropped when the run goes back to
`running`. Either way, the idle prompt's finish is the first one the outbox is
done with, and it is announced. A finish straight after a finish is announced
when it begins an episode, which only a `Stop` does. A stretch that went
through a wait does not stay in the rest's episode: the wait begins one
episode, and the work after it another, so the stretch's finish is announced
and unread like a turn's, because the person was asked something during it.

`AwaitingPrompt` is the recorded exception to the two-provider rule for the
same reason as `CompactionFinished`: it closes an existing state rather than
introducing a concept. It also ends a turn that stopped without saying so. A
run that is `running` or `compacting` and whose `runStartedAt` is at least
55 seconds old, such as one the person stopped with Esc and then compacted, is
ended as `Interrupted` ends it: `runStartedAt` is cleared, a new episode
begins, and the turn record is ended as interrupted. Claude sends the idle
prompt after its TUI has sat at the prompt for a minute, so one that arrives
sooner after a prompt belongs to the stretch before it, delivered late, and
the turn just begun is left open (`STOPPED_TURN_IDLE_SECS`).

A turn waiting on the person (`needsInput`, a question or a permission
prompt) ends the same way only when the transcript says the call it waits on
is over. Esc at Claude's question or permission prompt refuses the call before
it runs, so no `PostToolUse` or `PostToolUseFailure` follows, and Claude runs
no `Stop` for a stop the user interrupted. The transcript gains the call's
`tool_result` ("User rejected tool use", `toolDenialKind: user-rejected`) and
the line "[Request interrupted by user for tool use]", and the idle prompt is
the first hook after them. So the adapter reads the transcript tail on the
idle prompt (and on no other notification) and sets `awaited_call_ended` when
every tool call of the latest assistant message that made one has a result,
or an interrupt line follows it. A wait with that fact, in a turn open at
least 55 seconds, ends as interrupted; without it the wait stays, because a
minute idle is also a person who has not answered yet, and ending a live
question would hide it. A wait outside a turn (a late tool's permission) is
left as it is either way. The idle prompt writes nothing for any other run: a
run at rest already rests.

On a real Claude Code 2.1.309 run, the idle prompt did not come at all after
an Esc that declined a question: twice, nothing followed for 85 and 110
seconds. So the record cannot be the only place that ends the wait. The
call that opens a wait (the question tool's `PreToolUse`, the permission
prompt's `Notification`) names its transcript, and so does the prompt that
begins the turn (`UserPromptSubmit`); the record keeps it in
`transcriptPath` while the run is in the turn or waits
(`ProviderAdapter::turn_transcript_path`; nothing is read then). The app's projection pass asks, for each run that
waits inside a turn and names one, whether the transcript shows the wait
declined (`ProviderAdapter::transcript_shows_wait_declined`), and shows such
a run as its turn stopped: `finished`, with neither the wait's words nor its
kind, in the wait's episode, which announces nothing, and with the stop
reason `waitDeclined`, so the decision bar says the wait was declined rather
than answered. That badge is the instant answer. The same pass also returns
an `endStoppedTurn` command naming the turn as it read it: its episode
token, its turn, and its transcript. The app runs the command once per turn,
off its main thread (`StoppedTurnCloser`, at most three tries for a write
that does not land), through `limpid_stopped_turn_end_v1`. That writer is
the hook runtime's own (`limpid_agent_hook::end_stopped_turn`), and it ends
the wait as the idle prompt's `EndsStoppedTurn` does. The turn's end snapshot
and difference are taken before the record lock, as a hook takes them. Under
the lock the record is read again, and the write goes ahead only if it is
still that wait in the same episode and turn, naming the same transcript,
and the transcript still reads declined. The run record then ends
`finished`, outside the turn, without `waitKind` or `transcriptPath`, and its
turn ends `interrupted` with its end snapshot and what the transcript says
it used (`ProviderAdapter::transcript_turn_reading`, read as a hook's turn
end reads it: Claude reports itself idle a few milliseconds before the
stopped turn's last lines reach the file, so the reading waits up to a
second for a last response). The prompt the person types
next takes the same lock, so a write that comes after it finds a new episode
and writes nothing. Unlike the idle prompt, the write keeps the wait's
episode: the badge already showed the finish in it, and a new episode would
announce a second finish. Nor does it rebuild the record from a hook call's
identity: the app is the writer, so the record's own fields are carried. This
read is stricter than the idle prompt's: only an
interrupt line after the call counts. With no idle minute behind it, a result
alone is also an answered question or an approved command a moment before its
own hook moves the run on, and a refusal with words lets the turn go on. The
bridge's engine reads the transcript tail under the hook's limit and only when
its size or modification time changed since the last pass that asked
(`limpid_agent_hook::DeclinedWaits`), so an unchanged transcript costs a
`stat` per pass. The core names no file and no provider: the bridge answers
for it through the adapter.

"No" at Claude's permission prompt leaves no interrupt line, so the
transcript cannot say that wait is over. Claude says it itself: it reports its
status to the terminal over OSC 7501 (the Program Status Protocol) once the
terminal answers the protocol's support query, and after either answer it
reports `idle`. Our libghostty fork forwards each report about the program as
a whole, and the app keeps each pane's latest (`PaneProgramStatusStore`) and
hands it to every pass as `programStatus`, with the second the terminal
forwarded it. A provider names the `app` its agent reports under
(`ProviderDescriptor::program_status_app`, `claude-code`). A run that waits
inside a turn and whose pane last reported idle under that name, in or after
the second its record last changed, has had its wait declined, and the
transcript is not asked. Only the latest report counts, so an idle from
before the turn is no evidence: the turn's `working` and the wait's
`blocked` replace it before the record says the run waits. A refusal with
words lets the turn go on, so Claude reports `working`, not `idle`, and the
wait ends with the next hook as before. The command then says so
(`byProgramStatus`), and the writer checks the record under the lock as
before but does not read the transcript. Inside tmux, Claude asks tmux
rather than the terminal and reports nothing, and with
`CLAUDE_CODE_DISABLE_TERMINAL_TITLE` set it neither asks nor reports; the
transcript is then the only evidence, as it was. The same switch would have
kept Claude's own titles off the tab, which Rust names (`tab_titles`), so the
shim no longer sets it; the app leaves off every title from a pane while
an agent reports its status there, and the empty one Claude writes as it
exits. A pane's status goes when its program clears it, when its command
returns to the shell, or when the pane closes, so an agent that is killed
and sends no clear does not keep the shell's titles off the tab.

Esc or Ctrl+C while Claude works sends no hook either, and the transcript
says nothing of an Esc before the turn's first response. The record kept
saying the run worked until the next prompt, or an idle prompt if one came a
minute later. The report is the evidence here too. On Claude Code 2.1.312,
Esc before the first response, Esc while it wrote one, Esc while a tool ran,
and Ctrl+C each brought `idle` within 50 ms; a turn that ends on its own
reports `done`, an answer at the permission prompt goes straight from
`blocked` to `working`, and an Esc at a subagent's permission prompt that
lets the turn go on reports `working`. So a run at work inside a turn
(`running` or `compacting`) whose pane last reported idle under the
provider's name, in or after the second its record last changed, was stopped
by the person. Claude reports `working` as the prompt is sent, before its
hook writes the record, so the idle before a turn is never the latest report
once the record says the turn runs. The badge shows the turn stopped with the
stop reason `interrupted`, and the pass returns the same `endStoppedTurn`
command with `byProgramStatus`; the writer ends the run record
(`lastHookEvent` `interrupted`) and the turn as it ends a declined wait. Its
finish is not announced, since the person stopped it with their own key, and
the record keeps the episode, so it is not announced once written either.
Work is never read from the transcript: inside tmux, or with
`CLAUDE_CODE_DISABLE_TERMINAL_TITLE` set, it ends with the idle prompt as
before.

The end snapshot the idle prompt takes runs before the record lock, so the
hook judges the idle prompt again from the record under the lock and drops it
whole if the run has moved on in the meantime: if what it ends or the turn
step differs, or if the run's episode, `runStartedAt`, or `outsideTurnRest`
changed, even when the state reads the same again (a `Stop`, then another late
tool). A real `Stop` or a prompt that arrived during the snapshot changed what
the run shows, and the end prepared for the idle prompt would replace the
real one. The revision is not compared: every write moves it, and a write
within the same stretch changes nothing the idle prompt ends.

In the recorded payloads, the idle prompt comes only once the turn has ended
(after its `Stop` or `StopFailure`), never during a permission prompt; the
declined question case (`claude/2026-10/ask-user-question-declined`) is
written from the transcript lines Claude leaves, not recorded. Claude Code
2.1.312 sends no idle prompt if a dialog is on screen when the minute is up,
so a permission or question prompt never gets one, and it sends none at all
once the person has typed something after the response. Since 2.1.288 it also
holds the idle prompt back while a subagent runs in the background (a
background shell does not count), and counts the minute again once the
subagent ends. On a real 2.1.312 run, the minute after a turn's `Stop` passed
without an idle prompt while its background subagent worked; the subagent's
end started a turn of Claude's, and the idle prompt came a minute after that
turn's `Stop`. With only a background shell left, it came a minute after the
`Stop`. An idle prompt held back comes later, never sooner, so the rule that
it ends only a turn open for at least 55 seconds still holds. Should an idle
prompt come while the prompt is still open, the call has no result yet and
the wait stays. A wait that outlives its approval is a visible failure; a
wait settled while the person still had to answer would hide the request and
return the request the app holds to the TUI. The rare case that remains is a
request the app holds whose run the idle prompt settles from `running` before
the run reports the wait: the settled run reads as past its turn, and the app
gives the request back to the TUI, which still asks. Codex sends no idle
signal, and no recorded Codex case has a tool after its `Stop`, so a Codex
stretch ends at the next `Stop` or prompt. The shell receivers, while they
were the rollback path, had none of this: they reopened the run on a late
tool and left it running until the next prompt.

A stretch that began in `error` settles as `finished`, not back in `error`.
The agent went on working after the failure, and that work ended without a
failure. The failure was already announced and listed, and its stop item ended
when the run left the error, so returning to it would list the same failure
again. The settled finish stays in the failure's episode, which the outbox
counts as an end it is done with, so it is not announced either. While the
stretch runs, the run shows its tool, and a permission prompt in it names that
tool, never the earlier error.

Tool events open no turn record, inside a turn or outside one, with one
exception: a Codex hook of a turn Codex began itself, which no prompt opened.
Every hook inside a Codex turn names the turn (`turn_id`), so the runtime
begins such a turn at the first of them, while the run is in no turn and the
hook names a turn other than the run's last one. It applies a
`PromptSubmitted` before the hook's own events, under an id of its own
(`<call>#turn`) so a retry of the hook applies its events once, and takes the
begin snapshot before the hook's tool runs. A turn first seen at its end (a
`Stop` with no tool before it) takes none: whatever it changed happened
before the hook, so its begin is missing, as an end-only turn's is. A hook of
the run's last turn after that turn's `Stop` is the late work this section
describes, and begins nothing.

### Prompt cache window

`TurnFinished` carries an optional `cache: CacheWindow` with `observed_at` (the
record timestamp format), `ttl_seconds`, `rewrite_tokens`, and a `precision` of
`reported` or `estimated`; the record and the projection spell them in
camelCase on the wire (`observedAt`, `ttlSeconds`, `rewriteTokens`). It is an
observation attached to the event that ends a turn, not an event of its own:
it has no moment of its own to report, and attaching it keeps the vocabulary
rule above intact while only one provider supplies it. `None` means unknown and
is never read as "no cache".

The agent caches the conversation prefix on the model provider's servers for a
fixed time after the last request: an hour on a Claude subscription and five
minutes with an API key or usage credits. The next message after that re-writes
the whole prefix at the cache-write rate, which for a large session is the most
expensive message the user sends. The interface shows the window so the user
can decide before returning to a pane.

`apply` stores the window on the run record (`cacheWindow`, absent in older
records) when a turn finishes, and clears it on `PromptSubmitted`, every
`SessionStarted`, `SessionEnded`, `Compacting`, `CompactionFinished`, `Failed`,
`Interrupted`, and an `AwaitingPrompt` that ends work, because after any of
those the window no longer describes the cache. A window the reader cannot
decode costs only the window, never the record. `project` passes it to the badge
only for a provider with `cache_window`, and the interface derives "expiring
soon" and "expired" from it with its own clock, so the projection does not run
on a timer. "Expiring soon" starts when a fifth of the TTL is left, at most five
minutes ahead: an hour's window warns five minutes before it expires, a
five-minute window one minute before.

Claude Code exposes the expiry only on the status line command's standard input
(`prompt_cache.expires_at`). We do not install a status line to read it:
`--settings` outranks the user's settings files, so ours would replace the one
the user configured, and managed settings can own the key outright. No hook
field at `Stop`, no plugin API, and no OpenTelemetry attribute carries the
value; anthropics/claude-code#99905 asks for the plugin API to expose it. The
Claude adapter therefore estimates the window from the transcript tail it
already reads on `Stop`: the last main-thread request (lines grouped by
`requestId`, `isSidechain` lines skipped), anchored at that request's earliest
line, with the TTL named by the bucket its usage wrote
(`cache_creation.ephemeral_1h_input_tokens` or `ephemeral_5m_input_tokens`). A
request that only read the cache inherits the bucket of the nearest earlier
write; with no known bucket, or no cache counters at all, the window is unknown
rather than assumed to be five minutes. It is unknown too when a main-thread
user line (a tool result or a prompt) is newer than the last usage line, which
means the turn's final response was not yet written when `Stop` ran; anchoring
on the request before it would show the cache expiring early. `rewrite_tokens`
follows the plugin API's definition of the prompt the next request re-sends: the
last main-thread response's input, cache read, cache creation, and output
tokens.

The interface types the agent's own `/compact` or `/clear` when the user
answers from the expired clock's panel, so the projection also carries each
run's recorded `pid`. The host types only when that process, or for a
tmux-hosted run the tmux client forwarding to the run's active pane, is what
the pane has in front. A provider's declared process names are the fallback
for a run with no recorded pid, since an agent can run under an interpreter's
name.

Codex exposes no expiry today and does not declare `cache_window`. When it
does, its adapter fills the same struct, with `precision: reported` if the
value is stated rather than derived, and no record, projection, or interface
code changes.

### Rule functions

| | `apply` | `project` | `on_launch` / `on_terminate` |
| --- | --- | --- | --- |
| Status | Implemented | Implemented | Implemented |
| Runs in | the hook process (Rust inside the Hook Helper) | the application, on every watcher event | the application, before session bootstrap and in `applicationWillTerminate` |
| Input | previous record bytes (v2 or v3, or none), one `AgentEvent`, `HookContext`, the provider's capabilities, `now` | all record bytes, attention marks, tmux presence, live pane and PID sets, focus, resume intents, the previous `ProjectionState`, wall and monotonic clocks | record, resume intent, and resume hint bytes, live PID set, `now` |
| Output | `RecordWrites`: the run record (`schemaVersion: 3`) plus side writes for the resume hint, cwd event, and turn snapshot operations | `ProjectionState` (kept in the bridge's engine, never handed to the host), `Projection` (runtimes per pane, dominant badge and title per tab, notification transitions), `Vec<Command>` | `Vec<Command>` |
| Replaces | both `limpid-hook` event maps, hint and cwd writes, both worktree scripts | `AgentStateTracker` merge, dominance, notifications, and GC; `AgentSessionTracker`; `CwdEventTracker`; `WorktreeEventTracker`; `AgentLifecyclePolicy`; `AgentNotificationOutbox`; `applyTabTitle` (the pane header still resolves its title through `limpid_resolve_title_v1`) | Codex's launch cleanup and terminate preservation, applied to every provider with `resume` |

None of these rule functions owns a file, a timer, or a provider branch. They
describe side effects without performing them: the hook runtime executes the
`RecordWrites` returned by `apply`, while the application-side rules return
`Command` values that the Swift host executes under the record lock. Two clocks
are passed because record comparison and retention use wall time while the
notification outbox's pending lifetime uses monotonic uptime. Notification
delivery stays in Swift: `project` returns the transition, the target pane, and
the focus suppression condition, and the host decides whether the pane is
focused and applies rate limits.

### Command semantics

The application-side commands use
`{ op, target, expect, on_mismatch, then }`. `expect` is one of "exists",
"storageID, revision, pid, and updatedAt match", "pid and revision match", or
"hint owner matches". `on_mismatch` is `Continue` or `Abort` and says whether
the chained commands still run when the precondition fails. A lock conflict
always aborts. The Swift executor checks the precondition inside the file lock
and reports each outcome to the next `project` call. This expresses Codex's
"update only when pid and revision match, delete the resume intent only on
success" and "retire a dead record even when the hint belongs to another run"
as data rather than as tracker code.

### Records and the hook backend

State files continue to carry reduced records, not event logs, so the Swift
watcher and the directory layout stay. Records are decoded on both sides in
Rust: the hook writes them and the projection reads them, so Swift never
parses a record beyond the fields a command asks it to compare. `apply`
accepts a v2 record and writes v3, and revision monotonicity makes a writer
change in the middle of a run safe. The shim read `LIMPID_AGENT_HOOK_BACKEND`
(`rust` or `shell`) for one release, with the shell backend as the rollback
path. Both are gone now. The wrappers exec only the Hook Helper and, when it
is missing, fail the hook call and say why, because the shell receivers wrote
no turn records, and a fallback to them emptied the changes panel without a
word.

### Lifecycle and storage decisions

1. Every `SessionStarted` clears `lastPrompt` and refreshes
   `sessionStartedAt`. A non-compact start also clears `runStartedAt` and
   `firstPrompt` and replaces both title fields; a compact start retains those
   fields unless it supplies a session title, and keeps `runStartedAt`, since
   the turn it arrived in goes on (see "Work outside a turn"). The shell
   receivers cleared `runStartedAt` on every start. `runStartedAt` is also
   cleared by `TurnFinished`, `Failed`, `Interrupted`, `SessionEnded`, and the
   idle prompt that ends a stopped turn. Claude's `StopFailure` previously
   erased the last prompt that the error notification body is built from.
2. Kill markers on terminate and restore on launch apply to every provider
   with `resume`; the Codex-only scope was an accident of the generic
   extension it lived in.
3. `CompactionFinished` is a named event (see above).
4. A resume-hint precondition mismatch continues the chain; only a busy lock
   aborts. A hint owned by another run must not keep a dead record alive.
5. The unused pane-close path for state records is deleted; a closed pane is
   retired by the next projection through liveness and PID checks. Session and
   cwd deletions on pane close stay in Swift because they are user actions.
6. Directory names are declared by the descriptor (see above).
7. The worktree bootstrap step keeps `/bin/sh -c` with the same string and
   environment as the current `eval`; redesigning it is a separate task.
8. When the state directory environment is missing, the hook writes nothing
   and logs one line to `LIMPID_HOOK_LOG` if set. The shim always sets the
   variables, so their absence means the agent was not launched through
   Limpid, and falling back to the Release paths would mix Debug and Release
   data.
9. Pane-keyed legacy attention marks are removed; runtime-keyed marks are the
   only source and are rebuilt on the next scan.
10. A record whose process is confirmed dead is retired on the next pass
    whether or not its pane is still open, and a dead run with neither a kill
    marker nor a resume intent is retired at launch together with the resume
    hint it owns, for every provider. Resume therefore covers runs Limpid
    stopped itself and runs hosted in tmux; a crash of the agent, or of
    Limpid, is not resumed. The earlier Claude-only exemption read a surviving
    hint as evidence of a crash, but a provider's session-end report is lost
    the same way its process is, so the hint proves nothing.

### FFI

Message-shaped calls keep the hand-written C ABI with JSON envelopes. The
current bridge exposes approval exchange, approval translation, and a combined
hook entry point, and the application-side rules use the same convention: the
projection engine's pass (`limpid_projection_engine_pass_v1`) and the
lifecycle rules (`limpid_projection_on_launch_v1`,
`limpid_projection_on_terminate_v1`), beside the restore, discard, and turn
GC calls. The header is generated by cbindgen from the bridge crate and the
committed file is diffed in CI, so the header can no longer drift from the
exported symbols. New symbols carry a `_v1` suffix, and the bridge ABI version
moves only when an exported contract changes incompatibly. It moved to 3 when
the projection state stopped crossing the boundary. Each pass had handed the
whole `ProjectionState` back and forth as JSON; the state holds a summary of
every kept turn, and that round trip came to cost more than the rules
themselves. The state now stays in an engine that the host holds by an opaque
pointer (`limpid_projection_engine_v1`), and `limpid_projection_project_v1` was
removed. A pass proposes the next state under a number, and the host commits
that number once it has read the answer; a proposal made from a state another
commit has since replaced is refused. It moved to 4 when
`limpid_restore_recover_v1` stopped failing as a whole on one unreadable
journal. It now settles and returns the journals it could read, with
`isIncomplete`, where it had returned `LIMPID_TURN_UNREADABLE`. A caller
that does not know the flag would read an incomplete list as whole. Panics
never cross the boundary. Typed
records crossing the boundary would trigger an evaluation of a binding
generator, recorded in its own ADR.

### Conformance harness

Real payloads are recorded under
`rust/fixtures/<provider>/<schema-date>/<case>/`, scrubbed of paths, prompts,
and session ids, and paired with `expected.json` holding the neutral events per
payload. One driver in the model crate runs every provider crate against its
fixtures and against a shared negative set (truncated JSON, oversized payload,
non-object root, unknown event names). A provider schema change adds a dated
directory and keeps the old one passing.

## Consequences

The shell rules and the Swift approval translation are replaced by crates that
are tested on macOS, Linux, and Windows CI, and a provider is added as one crate
plus fixtures. Every hook event now launches the signed Hook Helper and runs
Rust in-process; the helper's `hook` subcommand opens no XPC connection, and the
accepted latency is a p95 of 50 ms or less per hook and no worse than the shell
implementation, measured over 200 consecutive `PreToolUse` payloads.

The Xcode script phase runs Cargo on every build, so the workspace size is a
build-time cost. The baseline before any new crate, recorded on 2026-09-14 with
`scripts/measure-build-time.sh` (Debug configuration, Apple silicon, medians of
three runs; the cargo rows are single cold and no-op runs in a scratch target
directory):

| Measurement | Seconds |
| --- | --- |
| Clean `make build` | 25.0 |
| Incremental `make build` after touching one Swift file | 4.9 |
| Cargo build of the bridge, cold | 6.8 |
| Cargo build of the bridge, no-op | 0.1 |

Fixture recording exposes user content; scrubbing is mandatory and the corpus
is reviewed like code. Two implementations of one rule existed in `main` only
during the one release in which the shell backend remained.

Swift keeps file watching, PID sweeps at the descriptor's interval, tmux
presence, the locked command executor, `WorkspaceSession`, `Tab`,
`AttentionState`, notification delivery, XPC, signing, `SMAppService`, and all
UI.

## Acceptance criteria

- The committed bridge header matches the cbindgen output in CI on all three
  operating systems.
- Adding a provider changes no source file in `limpid-agent-model` or
  `limpid-agent-core`; the adapter crate owns its fixtures and conformance
  tests.
- Each lifecycle and storage rule defined above has a corresponding Rust test
  or fixture case.
- The conformance harness passes for both providers with `normalize`
  implemented, and every negative fixture yields an error or one `Extension`.
- The hook latency budget above is met, and the build-time difference against
  the baseline table is recorded in the pull request.
- A run whose writer changes between the shell and Rust backends keeps a
  monotonic revision and produces one record.
